# The standards

Each one reports what in the diff falls short and the fix. Report only; the loop in SKILL.md decides and fixes.

## Cleanliness

**Simplicity.** The change can't get smaller without losing something it needs. List what it must do, then flag every line, branch, option, file or dependency that isn't needed for that, and every two things that could be one.

**Modularity.** Each part has one job and a small, explicit interface: it could be moved elsewhere by reconnecting that interface alone. Flag parts that only pass things through, reach into another part's internals, depend on each other in a circle, or take more than they use.

**Abstraction.** Every concept is real, sized right, and there are few enough to hold in your head. Flag a parameter only ever given one value, an interface with one implementation, a helper used once, and two things merged only because they look alike.

**Purity.** Logic between the edges (requests, the database, the DOM) is pure: same input, same output, no hidden state. Mutation is fine where it's the clear choice (a local accumulator, a ref), but it stays local and obvious. Flag copying large data just to look pure.

**Readability.** Each function reads like a short paragraph at one level of detail. Rules live in types, constraints or data rather than in branching code. Names say what something is; inline a name that tells the reader nothing.

## Robustness

**Design simplicity.** Step back from the lines: is this the simplest design that meets the intended behavior? Flag a mechanism where a plain function would do, state that could be derived, and work done on the server that the client already has (or the reverse).

**Security.** Correct under attack: who can call it, with what input, and what they gain. Check authentication, authorization (only the signed-in owner's data), input validation (zod at the edge), output escaping, secrets (never logged or sent to the client; `server-only`), cookies, CSRF, and unbounded work an attacker could trigger. Each finding names a concrete path. Flag a check that duplicates one that already exists.

**Edge cases.** Every case real use reaches (empty, one, many, very long, slow network, a reload mid-stream, two tabs, an error from NVIDIA), and rare ones whose failure would be bad (lost messages, a stuck spinner, a wrong chat). Give how likely and how bad.

**UI and UX.** Polished at every size (1440 and 390), in light and dark, by mouse, touch and keyboard, with worst-case data (`?data=worst`). Follows DESIGN.md and the no-slop rules, and matches grok.com where Grok has the same part (measure it in Chrome, don't guess). Flag desktop UI squeezed onto a phone, missing focus and loading states, and motion that fights the user.

- **ui-sdk first.** Read `node_modules/@ui-sdk/react/docs/llms.txt` and the `ui-sdk` skill. Flag any part, behavior or hook built by hand that ui-sdk ships (components, controllers, hooks, motion physics, agent tools), and any ui-sdk option left at a default the design overrides by hand. A hand-built part the diff touches moves onto ui-sdk.

**Performance.** Fast enough for Chat's real load (one person, long chats, big files): flag work that's repeated, unbounded, blocks a render or streams slowly. Also flag optimizing what that load doesn't need. Workers Free gives each request 10 ms of CPU: flag heavy server work (big SSR, hashing, parsing) that belongs in the browser.

**Tests.** The smallest set that gives real confidence (AGENTS.md › Tests): a smoke test per feature, a unit test for tricky logic. Flag a behavior change with no test, a test that can't fail, and any weakened lint, type or test check.
